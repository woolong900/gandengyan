# 热更新发布

客户端 1.0.6（资源基线 235）开始支持自己的 Cocos AssetsManager 热更新。旧版客户端会先收到整包升级提示，升级后才能使用资源热更新。

生成一个新资源版本（版本号必须递增）：

```sh
node tools/publish-hot-update.js \
  --version 236 \
  --stable-version 235 \
  --package-version 1.0.6 \
  --base-url https://gmhiu.com \
  --android dist/当前.apk \
  --ios dist/当前.ipa \
  --require-clean-git
```

脚本会从安装包清单中复制资源、重新计算每个文件的 MD5，并把 `project.jsc` 内的资源版本同步为发布版本，避免客户端重启后重复更新。输出目录包含 Android/iOS 版本目录、整包安装文件、iOS 安装清单和 `hot-update.json`。

正式发布前先提交代码；生成产物并验证后执行 `npm run release:mark -- --version 236`。该命令只接受干净工作区，创建 `release-r236` Git 标签，并把提交号写入 `release.json`。发布脚本也会记录构建时的提交号和脏工作区状态。

大型解包不再使用系统 `/tmp`，默认写入 `dist/.work`。可通过 `QJQP_BUILD_ROOT=/容量更大的目录` 指定独立构建盘。正式发布前会检查剩余空间，失败或成功后都会清理本次工作目录。

每次生成正式热更新或 PWA 后，会自动保留最近 10 个热更新、最近 5 个 PWA，并额外保护 R326、R328、R319 等构建基线。可先运行 `npm run release:prune:preview` 查看清理计划，再用 `npm run release:prune` 执行。

新版本默认作为“候选版”生成，灰度比例为 0%，不会自动推给全部玩家。`--stable-version` 应填写当前已经全量生效的资源版本；省略时只会按“候选版本减 1”推断，因此正式发布建议显式填写。只有明确需要立即全量时才使用 `--full-release`。

部署时先上传版本目录与安装包，最后原子替换 `/var/lib/qjqp/hot-update.json`；这样客户端不会看到半上传的版本。服务端无需重启，会自动读取新配置。

生产服务器安装 `deploy/qjqp-release-prune.service` 和 `.timer` 后每天自动清理：只删除当前配置未引用且超出最近 10 版的 Android/iOS 资源、超出最近 5 版且不是当前软链接的 PWA，以及超过 24 小时的构建暂存目录。

## 灰度验证流程

1. 在管理后台打开“热更新灰度”，确认稳定版本和候选版本正确。
2. 先填写测试玩家 ID 或测试设备灰度 ID，比例保持 0%，保存后只让指定对象更新。
3. 指定对象验证通过后逐步调整为 5%、20%、50%。设备使用稳定散列分桶，同一设备重复检查不会忽进忽出。
4. 验证完成后点击“验证通过并全量”，候选版会成为新的稳定版。
5. 发现问题时点击“停止继续灰度”。这只会阻止更多设备更新，已经更新到候选版的设备不会降级。

后台同页会显示最近 500 台检查过更新的设备，包括玩家 ID、系统、安装包版本、当前资源版本、目标版本、检查结果和最后检查时间。可以在设备行直接加入或移出指定灰度。设备数据来自启动时的版本检查；刚完成更新的设备要等下一次启动检查后，后台才会显示新资源版本。记录最多保留 5000 台，超过 180 天未出现的记录会在服务重启加载时清理。

新版客户端会在版本检查中携带本机生成的稳定灰度 ID，并保存最近一次成功登录的玩家 ID。尚未带此能力的旧客户端仍可按比例灰度（服务端使用来源地址与 User-Agent 确定性分桶），但无法按玩家 ID 精准指定。灰度名单中排除项优先于指定项。

回滚不能把版本号调小。应使用上一个稳定安装包的资源重新发布一个更大的版本号，例如 236 有问题，就把 235 的资源发布成 237。

## 整包与热更一致性

`tools/client-release-project.js` 是 Android 整包、iOS 整包与热更新的共用客户端脚本生成器。三条发布流程都从 `client-release-source` 生成完整 `project.jsc`，不再分别对旧包维护容易漏项的字符串补丁。因此：

- 新修复应先落到 `client-release-source` 的可编辑源码。
- 完整 Cocos Creator 2.4.13 恢复工程保存在仓库内的 `cocos-client`；正式发布流程仍以 `client-release-source` 为唯一输入，两者不会隐式混用。
- `patchapk.js`、`build-ios-ipa.js` 和 `publish-hot-update.js` 会自动携带同一批修复。
- `node tools/test-client-release.js` 校验三条流程仍使用共用生成器，并检查 2D/3D 碰后听牌提示等关键回归项。
- 整包中的序列化资源修复也必须与热更同步；当前已包含说胡子总结算四项统计行距修复。
